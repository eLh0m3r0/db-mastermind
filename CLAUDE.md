# DB Mastermind — maintainer notes

You are the sole maintainer (developer, PM, release manager) of this project. The owner is a product sponsor
who does not review code. Work autonomously: pick the next item from `ROADMAP.md`, ship it with tests, update
the roadmap, commit, push. Product decisions are in `docs/STRATEGY.md`.

## Layout

- `packages/core`: everything database-related, with no Electron dependency. Drivers (`src/drivers/*`), SQL
  dialects, filter → SQL builder, row mutations, script splitter, connection URL parser, `DatabaseService`
  (used by both the app and the MCP server). Source is consumed directly as TypeScript and bundled by the apps.
- `packages/mcp`: `dbmastermind-mcp` CLI, a stdio MCP server built on core.
- `apps/desktop`: Electron app (electron-vite). `src/main` is the main process (owns `DatabaseService`, settings,
  secrets), `src/preload` exposes a typed API, and `src/renderer` is React UI.
- `docs/`: architecture, strategy, user docs.

## Commands

```bash
npm install
npm run db:up                 # Docker: postgres:54329 mysql:33069 mariadb:33070 mssql:14339
npm test                      # unit tests (fast, no DB)
npm run test:integration      # every driver against real databases
npm run typecheck
npm run dev                   # desktop app with HMR
```

`DBM_SKIP=mssql npm run test:integration` skips engines that aren't available.

## Conventions

- TypeScript strict, ESM, no default exports except React components where idiomatic.
- Values crossing IPC/MCP are `CellValue` (see `values.ts`): never pass Date/Buffer/bigint across.
- Every SQL built from user input is parameterized; identifiers go through `dialect.quoteIdent`.
- Read-only connections are enforced in `DatabaseService` (statement classification) and at the database
  session level where supported. Don't bypass `DatabaseService` from the app.
- New driver = implement `DatabaseDriver`, add to `createDriver`, add a fixture to
  `test/drivers.integration.test.ts` and a service to `docker-compose.test.yml`.
- Comments explain *why*, not what. Keep them sparse.
- UI text is English; Czech translations live in the i18n files.

## Gotchas learned the hard way

- mysql2 emits `fields` with `undefined` for statements without result sets.
- mysql2 parses MariaDB JSON (BLOB + json hint) into objects; `typeCast` re-stringifies it.
- `KILL QUERY` must complete before a connection is reused, or it can kill the next statement.
- node:sqlite can't be interrupted; cancelling abandons the worker and opens a fresh one. A worker stuck in a query
  keeps the process from exiting, so before-quit exits hard when `sqliteWorkersAlive()` is still > 0 (e2e/flow86).
- pg user queries use identity type parsers (exact text); catalog queries must use `pg.types`.
- PostgreSQL editor tabs get their own `pg.Client` (`sessionClient`), never one from the 6-client pool: tabs keep theirs
  until closed, and pool-held tab sessions starved the grid, explorer and Cancel. Short-lived sessions (`readonly-`,
  `script-`, `copy-`, `explain-`) still borrow from the pool. Test: postgres-sessions.integration.test.ts.
- Editor function completions: `packages/core/src/functions/*-catalog.ts` are generated by `node scripts/sql-functions.mjs`
  from the running PostgreSQL container, DuckDB and node:sqlite; rerun it after bumping those versions.
- npm optional-deps bug: if rolldown/vitest says "Cannot find native binding", delete `node_modules` and
  `package-lock.json` and reinstall.
- DuckDB: one connection per statement (interrupt cancels a whole connection). File databases checkpoint after
  every commit (`checkpoint_threshold = 0b`): DuckDB 1.4 fails replaying some WAL entries, and a second
  instance on the same file needs the data in the file. A table with indexes, views or incoming foreign keys
  can't be ALTERed: `generateMigration` drops/recreates indexes and views around it, creates new tables last,
  and warns about referenced tables.
- DuckDB bindings are per-platform npm packages: release.yml fetches the other architecture's binding with
  `npm pack`, `build/after-pack.cjs` keeps only the target's binding in each package.
- `runScript` without a session runs multi-statement scripts on a temporary session, so BEGIN … COMMIT stay
  on one connection.
- This checkout lives in an iCloud-synced folder: never package the app locally into `apps/desktop/release`
  (hundreds of MB keep iCloud busy and file access hangs for minutes). Package to a temp dir instead:
  `npx electron-builder --dir -c.directories.output="$TMPDIR/dbm-release"`.
- Running e2e flows on the owner's Mac: set `DBM_E2E_BACKGROUND=1` (development builds only) so the app gets no Dock icon and never becomes active; its window opens on the primary display (macOS moves a window placed off every screen onto the nearest display, which was the owner's second monitor); give each flow a throwaway HOME. Flows that use PostgreSQL need `npm run db:up` (at least `postgres`) and the `shop` fixtures, seeded by `DBM_SKIP=mysql,mariadb,mssql,ms,duckdb,sqlite npx vitest run --project integration packages/core/test/drivers.integration.test.ts` (integration tests run only through `--project integration`; `--root packages/core` silently runs none of them). Reseed before each flow that edits the fixtures (flow2 renames Alice). flow46 needs a database `dbm_backup_test` with a table, flow61 a database `huge` with schemas `app1`…`app20` of 250 tables `t001`…`t250` each, chained by foreign keys (`scripts/e2e-extra-fixtures.sh` creates both; recreating the postgres container loses them); flow13 and flow24 take a file as their second argument; flow115 imports a project whose compose file publishes PostgreSQL on 54329 and connects with its password (needs `postgres`); flows 112–114 need no database; the AI flows (21, 31, 45, 79, 80) need a signed-in Claude Code or Codex and the real HOME, where the CLIs keep their sign-in (with a throwaway HOME they report "Not logged in"); their app data stays in a temp `DBM_USER_DATA`.

- BigQuery: filter values are text and BigQuery is strictly typed, so `Dialect.typedParam` casts them to the column type (engine passes `columnTypes`); LIKE has no ESCAPE clause (backslash). The emulator (goccy 0.8.1, port 19050 in tests) ignores LIKE escapes and rejects duplicate result column names — real BigQuery handles both, so tests avoid them.
- Shortcut text in the UI goes through `keys('⇧⌘↵')` (lib/api) so Windows/Linux show Ctrl+Shift+Enter; never hardcode ⌘. To see the app on Windows/Linux, run the `UI tour` workflow (workflow_dispatch) and download its screenshot artifacts.
- Trino driver speaks the HTTP protocol with fetch (no client library): `{__pN}` placeholders are inlined as literals and cast to the column type by `trinoDialect.typedParam` (Trino won't compare varchar with numbers/dates). 64-bit integers stay exact through `JSON.parse` with the reviver's `context.source`. Result column types use the protocol's spelling (`decimal(10, 2)`, `timestamp`), the schema uses information_schema's (`decimal(10,2)`, `timestamp(3)`). Local test server: `docker run -p 18080:8080 trinodb/trino:483` (memory + tpch catalogs).
- AI/MCP SQL nobody confirmed runs with `runScript(..., { readOnly: true })`: a read-only transaction (`dialect.beginReadOnly`) on its own session, always rolled back. Statement classification alone is not a guard (`SELECT setval(…)`, functions that write, T-SQL `SELECT 1 DELETE …` without semicolons). Read-only SQL Server connections use the same guard (ApplicationIntent=ReadOnly only binds on replicas). Tests: packages/core/test/readonly-guard.integration.test.ts.
  - "Is it a read?" is `isReadOnlyScript(sql, driver)`, never `classifyStatement` alone: for T-SQL it scans the whole statement for writes/EXEC/COMMIT; SQLite pragmas are reads only from an allowlist; `DECLARE … BEGIN` is not a read. Raw grid filters must pass `isReadOnlyCondition` on every connection (engine fetchTable/countTable).
  - SQL Server: never `request.cancel()` a batch that may write (it stops the rest of the batch); only read-only batches stop early at maxRows.
  - SQLite has one connection: `releaseSession` rolls back only the transaction its own session opened (the worker reports `isTransaction` with each reply).
- Editor transactions (Milestone 10): the state comes from `driver.transactionState(session)`, never from parsing SQL (PG: protocol status, wait for ReadyForQuery after an error; MySQL: OK packet SERVER_STATUS_IN_TRANS, InnoDB's INNODB_TRX lags 0.1 s; SQL Server: `@@TRANCOUNT`/`XACT_STATE()`; DuckDB: `txid_current()` twice — a second BEGIN aborts a DuckDB transaction, so never probe with it). `runScript(…, { editor: true })` applies `manualCommit` (`opensTransaction` decides what opens one) and notes implicit DDL commits. SQLite refuses writes from another tab while one tab owns the transaction. Quitting/closing/disconnecting settle open transactions first (main/transactions.ts, store/transactions.ts); saving a connection reconnects only when `needsReconnect`. Tests: transactions.integration.test.ts, e2e/flow98.
- Dropped connections (server restart, VPN, idle kill): drivers keep `SessionTransactions` per session. No open transaction → reconnect/retry silently (retry only when it can't apply a write twice); open transaction → `ConnectionLostError` once, never silent autocommit. PG checked-out clients need an 'error' listener or the main process crashes. SQL Server reuses SPIDs, so it checks `@@TRANCOUNT`. Test: connection-loss.integration.test.ts (kills sessions from an admin connection).
- SSH host keys are trust-on-first-use (core/ssh.ts `useKnownHostsFile`, `<userData>/known-hosts.json`, shared with the MCP child); a changed key throws HostKeyMismatchError; the connection form shows the key with Forget. Writes are atomic and an unreadable file refuses the connection (never treat it as empty). e2e/flow63.
- SSH tunnels (core/ssh.ts) reconnect lazily: the next forwarded socket re-opens the SSH connection. ssh2 Clients need a permanent 'error' listener and `forwardOut` can throw synchronously — both used to crash the app. Test: ssh.integration.test.ts against the `ssh` service (container `dbm-ssh`, restarted by the test; DBM_SSH_KEY for key auth).

Test: tls.integration.test.ts with scripts/tls-test-servers.sh (test CA, pg-tls :54330, my-tls :33071).

- macOS saved secrets: packaged apps encrypt them with AES-256-GCM (`enc:v2:`) using a key kept in the login keychain and read through /usr/bin/security (storage.ts `macSecretKey`, one key per data folder); `enc:v1:` (Electron safeStorage) is read once more and re-saved. safeStorage's item asked after every update because macOS partitions keychain access by cdhash for apps without an Apple Developer ID — a stable self-signed certificate does NOT fix that. Dev/e2e runs keep safeStorage unless DBM_MAC_SECRET_KEY=1. The key is created only when `security` exits 44 (item not found) and never overwritten (`readOrCreateMacKey`). A secret that doesn't decrypt is kept as ciphertext by `UnreadableSecrets` and written back on save, so a keychain hiccup never erases passwords (e2e/flow84).
- Nothing asks the keychain before there is a secret the user gave us (1.5.0 and 1.5.1 showed "Keychain Not Found" twice at the first start on a new Mac; fixed in 1.5.2): a fresh profile has no MCP token (made when the endpoint is turned on, `settings.ts` `tokenToStore`; a plain token from before 1.5.0 is encrypted only once a key is in use or the endpoint is turned on). A Mac user without a default keychain (`security default-keychain -d user` exits 1, or its file is gone: `hasDefaultKeychain`) never gets `find`, `add-generic-password` or safeStorage (the last two each show that dialog): secrets are stored `plain:` and the forms say so (`secretsWithoutKeychain` → 'mac-keychain'); "no keychain" is asked again after 3 s, so a keychain the user makes meanwhile is used by the next save, and what was stored plain is encrypted on the next start (the legacy re-save). A keychain that exists but doesn't give the key (locked, refused, timed out) still falls back to safeStorage for the session, as before: never to plain text. `DBM_DEBUG=1` logs every `security` command and safeStorage call by name. A throwaway HOME has no default keychain, so e2e runs store secrets `plain:`. Tests: keychain-start.test.ts (fake `security` and safeStorage; never the real keychain).

- DeZign for Databases models (core/dezign.ts, main/dezign-file.ts): element-only XML read by a tolerant tokenizer that serializes back byte for byte (the base for saving in place, ROADMAP 8.2). Quirks: empty settings written as `<X /></X />`; the `iso-8859-1` declaration lies (bytes are the Windows code page of the author's machine, so files are read as binary strings and decoded by `detectDezignEncoding`, with the app locale deciding ties); attribute ids are per entity in old formats and global in new ones; a relationship's parent can be a subtype cluster (`SUBCAT` → `AOID`); folder projects name files by object name before 14.5.1 and by id after. Real models never go into the repository: tests build their own (dezign.test.ts, e2e/flow91), and `DBM_DEZ_SAMPLES=<folder>` / `DBM_DEZ_FILE=<file>` run the reader and the app against local files printing counts only; with `DBM_DEZ_WRITE=1` flow91 also edits and saves that file (only ever on a copy).
- A model tab may have no connection (`connectionId: ''`; `useCurrentConnectionId` then falls back to the selected one): anything in ModelView that needs a database must check `connection`. Files handed to the app (argv, macOS `open-file`, second instance) go through main/opened-files.ts: the page pulls the ones that arrived before it was ready (`takeOpenedFiles`) and then calls `bridge.listenForFiles()`. Tabs are saved 400 ms after a change, so an e2e flow must wait before `win.reload()`.
- DiagramView stores positions, notes and colors on its tab unless `onLayout` is given: ModelView uses it to keep them per named diagram (`ModelTab.diagrams`, from the DeZign source) and passes the whole-model ones through the tab. DeZign colors are Delphi `0x00BBGGRR` numbers in `BRUSH`; main/palette.ts maps them to the series palette.
- Saving to DeZign (core/dezign-write.ts `saveToDezign`, main `saveDezignModel`): the edited DBML is compared with the source's own DBML round trip (`normalize`), so a detail DBML loses is never a change; tables and columns are matched by name, then renames are guessed (table: ≥ 60 % shared columns; column: same type in the same place) because DBML text has no identity. Objects are numbered in old files (next number) and GUIDs in new ones. The result must read back equal to the target or nothing is written. `DBM_DEZ_DEBUG=1` prints the mismatch — use it only with public samples, never with a private model; `DBM_DEZ_DEBUG=shape` prints only the differing lines with every name, text and number masked (safe with a private model). Switch target database: `targetDatabase` writes DBID (single file: DATADICT; folder: the `.dds` file) and renames every DTLISTNAME to the PostgreSQL list's own name (`PG_LIST_NAMES`); verification compares types through `sameTypeName` (varchar ≡ character varying). Notation: DIAGRAM/NOTATION 0 crow's feet, 1 IDEF1X (`DezignDisplay.notation`; written only when a request names one). To-do items: `TODO` right after an object's ID (before POSNR), removed when empty and from clones. Labels: definitions in VERSION/LABELS (not in DATADICT; a folder project's `labels/` folder), on objects `OBJLABELS` after POSNR and USERDEFPROPS (DeZign's order) with one name a line (each ending in a line break). Subtypes: `ForeignKeyInfo.subtype` (DBML `subtype: true`) is a relationship whose PARENTOBJECTID is a SUBCAT (AOID = supertype) with RELTYPE 2; the writer makes the cluster once (SUBCAT + SUBCATEGORYCONNECTION + SUBCATC/SUBCATEGORYCONNECTOR per diagram of the supertype) and keeps the `subcategories` map live so relationships still match by signature. Custom properties: definitions in DATADICT `USERDEFINEDPROPERTIES/USERDEFPROP` (NAME, ID, POSNR, PROPTYPE `Text|Number|Yes/No|Value from list`, OBJECTTYPES, LISTVALUES one per line, GROUP); values on the object right after POSNR as `USERDEFPROPS/UDP_<id>`, in definition order; `Properties:`/`properties:` JSON in DBML. New procedures: `PROCEDURE` with NAME, a GUID ID, POSNR (next), CODE. Triggers live in their ENT (`TRIGGERS/TRIGGER`: NAME, ID, POSNR, …, CODE; ids `TRG-<table>-<n>-<token>` in DeZign 14, else per-table numbers with `TRGLASTID`), sequences and procedures in DATADICT (`SEQUENCES`, `PROCEDURES`; folder: `data dictionary/sequences|procedures`); a sequence's CYCLE is the database's own word from `seqcyclecodes` in DeZign's `.def` (`;cycle`, `nocycle;cycle`, `NO CYCLE;CYCLE`), never `1`. The app edits them as `tab.sqlObjects` and main turns the difference into `dezignObjectEdits`. DeZign's own sample models count as made with the full version: the trial opens only files it saved itself (the kit base). Attribute packages: a column keeps `PKGNAME` + `PKGITEM` (its place in the package, from 0) right after `</DT>`; the package definitions live in DeZign's installation (`packages/<dbid>/<name>.apk`, element-only, CRLF), never in the project, so `attributePackages(tables)` reads them off the columns that use them and the writer numbers a new member like the same-named column elsewhere (`packageColumnsFor`, `leavesPackage`). DeZign 14.9.3 propagates a changed .apk to columns linked this way. A batch rename tells the writer which table became which (`renamedTables`: a table whose every column was renamed shares no column name with its old self); a check whose condition changed only by renamed columns is rewritten in place (`renameInCondition`, which skips quotes and comments; conditions in the file may span lines with `--`, compared through `checkOneLine`).
- What DeZign itself taught (scripts/dezign-check: DeZign 14 under Wine in Docker opens a kit of saved files and saves them again; `DBM_DEZ_KIT_TO` + `DBM_DEZ_KIT_BACK` with test/dezign-kit.test.ts compares, `DBM_DEZ_REPORT=<file>` collects the lines): an empty number anywhere stops the whole project from opening (never empty a numeric field of a clone: give it the usual value); DeZign makes every name from its `NAMETEMPLATE` again on opening, so a typed name is written as its own template (`setName`), a clone whose template is its neighbour's typed name goes back to the project's pattern (`ownTemplate`), and pattern names follow a renamed table; projects upgraded to 14 number tables but give columns and indexes `ATTR-/IDX-<table>-<n>-<token>` ids (`styledChildId`): a plain number there is renumbered by DeZign and references from other tables are lost; a relationship's constraint id is `1` before format 140 and `<rel>-FK` in it; DeZign knows no character references (`codec.fit` writes the plain letter; `saveToDezign` fits baseline and target first, so a second save is a no-op); decode with `dezignDecoder`, never `TextDecoder('windows-1252')` (Node 24 reads it as Latin-1). Clones also `forget` labels and custom properties. A project of DeZign 11.1 or older is converted when DeZign 14 opens it.
